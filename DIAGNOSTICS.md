# KKOS v5.2.0 — Build Diagnostics Reference
Kurfew Kult Operating System

This document explains what the diagnostic log files mean and how to resolve each failure pattern.

---

## Diagnostic files produced during build probing

| File | What it records |
|---|---|
| `gppver.txt` / `gpp_stdout.txt` | g++ `--version` output — confirms compiler is found and shows rev |
| `gppv_stderr.txt` | g++ `-v` verbose config — confirms UCRT64 target, thread model, LTO support |
| `gppv_compile_stderr.txt` | cc1plus invocation for a test compile — shows include path resolution |
| `gppv_compile_exit.txt` | Exit code of test compilation |
| `gppv_kkos_stderr.txt` | cc1plus invocation specifically for `kkos_v520_unified.cpp` |
| `gppv_kkos_exit.txt` | Exit code of KKOS source compilation |
| `gppv_exit.txt` | Exit code of g++ `-v` itself |
| `test_build.log` | Captured build output (was empty — stderr not redirected) |
| `test_stdout.txt` / `test_stderr.txt` | stdout/stderr of test compile |
| `test_compile_exit.txt` | Exit code of test compile |
| `test_sp_exit.txt` | Exit code of subprocess launch |

**Compilation exits 1 on both test file and `kkos_v520_unified.cpp`.**

## Root cause analysis

The stderr from `gppv_compile_stderr.txt` cuts off at:
```
cc1plus.exe -quiet -v -I Single-Exe-1.0.0/raylib-5.5/src ... src/kkos_v520_unified.cpp
```

This means cc1plus was invoked correctly but its output (the actual errors) was not captured. Most likely cause in order of probability:

### 1. Missing raylib headers (most likely)
The `-I Single-Exe-1.0.0/raylib-5.5/src` flag is present, but if `raylib.h` doesn't exist there, every `#include "raylib.h"` in the source fails immediately with a fatal error that filled stderr (which wasn't saved).

**Fix:** Run `BUILD.bat diag` — it checks for `raylib.h` explicitly. If missing, ensure `Single-Exe-1.0.0\raylib-5.5\src\raylib.h` exists in the project root.

### 2. Stderr not captured in old build scripts
The old scripts used `>>build.log 2>&1` inconsistently. Some phases wrote stdout only. The new `BUILD.bat` always captures both streams and prints the last 30 lines on failure.

### 3. Source-level compile errors in `kkos_v520_unified.cpp`
If the source has C++17 errors, they would also exit 1. Run:
```bat
BUILD.bat diag
```
This runs `-fsyntax-only` and prints all errors inline.

## How to read the new build.log

`BUILD.bat` now always redirects both stdout and stderr:
```bat
"%CC%" ... >> "%LOG_DIR%\build.log" 2>&1
```

On failure, it also prints the last 30 lines directly to the console via PowerShell.

## Common errors and fixes

### `0xc0000139` at runtime (DLL not found)
MSYS2 UCRT64 runtime DLLs are not on PATH when running from Command Prompt or Explorer.

The launchers (`start-all.bat`, `start-kkos-only.bat`) prepend `C:\msys64\mysys64_new\ucrt64\bin` to PATH before launching the exe, which resolves this.

If running the exe directly, either:
- Add `C:\msys64\mysys64_new\ucrt64\bin` to your system/user PATH, or
- Copy these three DLLs next to the exe in `bin\`:
  - `libstdc++-6.dll`
  - `libgcc_s_seh-1.dll`
  - `libwinpthread-1.dll`

### `fatal error: raylib.h: No such file or directory`
raylib headers are missing. Ensure the bundle contains:
```
Single-Exe-1.0.0\raylib-5.5\src\raylib.h
```

### `g++ not found` / `COMPILER_NOT_OK`
Run:
```bat
BUILD.bat diag
```
Follow the install instructions printed. Confirmed working path: `C:\msys64\mysys64_new\ucrt64\bin\g++.exe`

### `Property miDebuggerPath is not allowed` in VS Code
Your `launch.json` is malformed or using the wrong type. The correct type is `"cppdbg"` (not `"cppvsdbg"`). The `.vscode\launch.json` generated by `BUILD.bat vscode` is correct.

### GDB not installed
```bat
install-gdb.bat
```
Then verify: `C:\msys64\mysys64_new\ucrt64\bin\gdb.exe` exists.

## Second diagnostic wave — all logs empty, all exits 1

From the second batch of files (`build.log`, `build_bash.log`, `build_cmd.log`, `build_ps.log` all empty; `compile_exit.txt`, `gpp_h_exit.txt`, `gpp_sp_exit.txt`, `gpp_stderr.txt` all exit 1 with empty stderr):

### Root cause confirmed: wrong working directory

`gpp_h_exit.txt` is the key. A header-only compile probe (`#include <iostream>`) exiting 1 with **empty stderr** means the subprocess was launched but could not find the source argument — which only happens when the file path is relative and the working directory is wrong.

All four build logs being empty confirms stderr was never redirected to disk at all in those invocations.

**The fix is the first line of every script in this integration:**

```bash
# Shell scripts (build.sh, start-macos.sh, etc.)
cd "$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
```

```bat
:: .bat scripts (BUILD.bat, LAUNCH.bat, etc.)
cd /d "%~dp0"
```

This unconditionally changes the working directory to the folder containing the script before any other code runs. All relative paths then resolve correctly regardless of where the script was double-clicked or called from.

### gpp_sp_exit (subprocess exit = 1)

`gpp_sp_exit.txt` = 1 means the outer subprocess launcher (PowerShell or cmd) returned 1 when spawning g++. Combined with empty stderr, this is consistent with a working directory problem: g++ was found, it was launched, but the source file argument resolved to a non-existent path and g++ exited 1 without printing to the (uncaptured) stderr.

### What to verify is fixed

After deploying these scripts, run:
```bat
BUILD.bat diag
```
or
```bash
./build.sh diag
```

You should see:
- `[ok] src/kkos_v520_unified.cpp exists`
- `[ok] Standard headers accessible`  (was the gpp_h test)
- `Exit code: 0` on the syntax probe

If the syntax probe still fails, the issue is in the source file itself — errors will now be visible in the terminal and in `logs/build.log`.
